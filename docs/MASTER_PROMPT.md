F. PHASE 3: CONNECTION STATE MACHINE (M1)
=================================================================
- ONE `ConnectionManager` (Hilt-provided, owned by the :vpn process) with states Disconnected, Connecting, Connected, Reconnecting, Disconnecting, Failed(reason). All commands (connect, disconnect, switch, reconnect) go through a single actor/Mutex and are idempotent. UI, tile, widget, notification, shortcuts only send commands and observe ONE state flow.
- Disconnect has absolute priority: cancels connect/reconnect/latency tests/auto-tune, sets `userRequestedDisconnect=true` (disables every auto-reconnect, auto-connect rule and kill-switch re-arm until the user connects again), closes the engine with a 3 s timeout then forces it, closes the TUN fd, removes the foreground notification, stopSelf, returns START_NOT_STICKY. Worst case <= 3 s, never on the main thread.
- Kill switch applies ONLY to unexpected drops; a user disconnect always fully releases everything; if the kill switch is blocking traffic, the notification and app offer "Disconnect and allow internet".
- "Connected" is shown only after a real HTTPS request through the tunnel succeeds; otherwise "Connected, but no internet through this server" with the exact reason and a one-tap "try next best server". Surface core errors (TLS verify failed, auth failed, handshake timeout, DNS failure) in the UI and masked logs.
- Handle: VPN revoked, VpnService.prepare() denial, process death, airplane mode, network changes (debounced ~500 ms to one reconnect), double taps, disconnect during Connecting/Reconnecting, rapid connect/disconnect. Reconnects use exponential backoff with jitter and a cap.
- Tests: every state x command, races, virtual time; connect/disconnect loop x100 with no leaked tun/service/notification/thread/fd; disconnect from tile, notification, widget; `dumpsys connectivity` shows no VPN and no tun after disconnect.

I. BATTERY AND EFFICIENCY (TOP PRIORITY after the project builds; M3)
=================================================================
I1. ROOT-CAUSE TRIAGE FIRST (internal spinning). Check and fix with code evidence (simple readings from an emulator/device are welcome but optional):
 1. TUN read/write path: non-blocking fds polled in a loop, `read` returning 0/EAGAIN without blocking (missing poll/epoll), loops that never suspend, multiple readers on one fd, a loop re-reading its own output. Reads must block (or poll); writers respect backpressure.
 2. Internal packet loops: core sockets not protected/bound, server domain resolved through the tunnel, DNS recursion through the tunnel, the app's own package mishandled. Add a debug counter of packets per UID and a loopback test.
 3. Spinning coroutines/threads: `while(true)`, `while(isActive)`, `repeat(Int.MAX_VALUE)`, `delay(0)`, tiny delays, `Thread.yield`, `tryReceive` polling, flows emitting in tight loops, StateFlow/SharedFlow collectors re-emitting each other, `retry`/`retryWhen` without backoff, `callbackFlow` without `awaitClose`.
 4. Duplicate/zombie instances: more than one engine/TUN reader/service after connect/reconnect/tile/widget/process restore; threads surviving disconnect; START_STICKY loops. Name every thread/dispatcher; log live threads after connect and after disconnect.
 5. Native runtime caps: Go-based engines can burn several cores; cap them: set GOMAXPROCS to 2 (environment variable before the native library loads, or the library's option), apply the engine's memory limit/GC tuning if exposed (check the real API), limit hev-socks5-tunnel worker threads, limit Kotlin dispatchers (`limitedParallelism`). These caps bound the worst case; the root-cause fix is still required.
 6. Engine config costs: gVisor stack, process lookup, sniffing, connection tracking/API polling, mux, aggressive keepalive/ping, uTLS, debug log level, DNS cache off, observatory intervals, large geo datasets in memory.
 7. A "connected" tunnel that passes no traffic makes apps (Telegram) retry aggressively and burns CPU in the engine: verify once after connect and report the real state; never loop on it.
I2. SHOW-ONLY-WHEN-LOOKED RULES (the user's explicit request):
 - NOTHING UI-related runs while nobody looks. Speed, traffic counters, charts, live connections and logs views are produced ONLY while a subscriber exists (`SharingStarted.WhileSubscribed`, `repeatOnLifecycle(STARTED)`); in the background or with the screen off there are no collectors, no timers, no animations (`rememberInfiniteTransition`/`LaunchedEffect` loops bound to visibility), no chart sampling.
 - The engine exposes CUMULATIVE byte counters; reading them is cheap. Speed = delta between two reads, computed only when someone is subscribed (1 Hz while the app is visible). When the user opens the app, the first read gives correct totals and an immediate speed within one tick; the chart starts live and fills from then on. History for reports is recorded from counter snapshots at EVENT boundaries (connect, disconnect, screen on/off, network change), never by a background timer.
 - NOTIFICATION POLICY: Android offers no public API to know that the notification shade is open, and you must not use accessibility services, restricted/deprecated broadcasts or hacks for that. Implement the setting "Speed in notification": (a) "Off": static content, with the elapsed connection time shown by the SYSTEM through `setUsesChronometer(true)` + `setWhen(connectTime)` (zero app wakeups); (b) "Screen on" (DEFAULT): with the screen off or the device locked the notification is static; on ACTION_SCREEN_ON / USER_PRESENT post ONE fresh update, then update at most every 3-5 s ONLY while the device is interactive and unlocked, and stop immediately on screen off; skip updates when the text would not change; `setOnlyAlertOnce(true)`, no sound/heads-up, stable `setWhen`; (c) "Always" (every 2 s, with a battery warning). The foreground notification channel is IMPORTANCE_LOW. Tile and widgets refresh on state events, not on timers.
 - The traffic chart must not be "always showing DL": it renders only when visible, shows an idle state when there is no traffic, and has no running animation off-screen.
I3.
